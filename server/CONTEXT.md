# server/ – Intranet API

**Step 3.** Fastify on Node 20, deploying to Azure App Service. Plain ESM
JavaScript with Zod at the boundary.

## What it does today

Serves every response the front end needs, from **generated fixtures** rather
than from SharePoint. That is the point of this step: the app gets a real HTTP
boundary — latency, CORS, status codes, failures to handle — before any external
dependency has been approved. Step 5 then swaps one domain at a time.

```
npm install
npm start          # http://localhost:3000
npm run dev        # with --watch
```

Point the front end at it with `VITE_DATA_SOURCE=api` in the root `.env`.

## Why plain JavaScript, not TypeScript

The backend plan recommended TypeScript. It was not used, deliberately: the
contracts in `src/contracts/` are plain JS shared by both sides, the team writes
JS, and Zod already validates at the boundary — which is the check that actually
matters for data arriving from SharePoint and HRMS. A TS server consuming JS
contracts would add a build step for types that could not flow anyway.

## Layout

| Path | Role |
|---|---|
| `src/app.js` | Builds the Fastify instance without starting it, so it can be tested with `inject()` |
| `src/config.js` | Every env value, resolved once with its default |
| `src/lib/store.js` | Reads fixtures. **The seam step 5 unpicks** — each read becomes a SharePoint call |
| `src/lib/cache.js` | In-process TTL cache, 5 minutes |
| `src/lib/contract.js` | Imports `src/contracts/` and validates responses before they leave |
| `src/routes/` | `content` · `csr` · `letters` · `admin` |
| `fixtures/` | Generated by `npm run fixtures` at the repo root. Committed, so the server runs standalone |

## Rules

- **Never hand-edit `fixtures/`.** They are generated from the mock adapters and
  validated against the contracts; edit the mock and regenerate.
- Every response goes through `validate()`. Development throws on a contract
  violation, production logs and sends — a drifted optional field should not
  take the homepage down.
- A "not found" is `404` with a `null` body, which the client adapters turn back
  into `null`. Reserve non-404 errors for things that actually went wrong.
- Per-user data (`/csr/me/stats`) is **never cached** — the cache is shared
  across every employee.
- Routes never touch the filesystem directly; they go through `store.read()`.

## Not built yet, and why

- **Auth.** Step 4. Every route is currently open; it binds to localhost in dev
  and must not be exposed until token validation lands.
- **Postgres.** Nothing writes yet. Feedback, volunteer signups and the gatepass
  are step 4 on the plan's numbering.
- **The letter issuance log** is a structured log line, not a table. It becomes a
  Postgres row when HRMS supplies the real employee record — logging the issuance
  of a fake employee's letter protects nobody.
